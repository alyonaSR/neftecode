# Советчик режима для производства товарного дизельного топлива

Мультиагентная система для цепочки АВТ → гидроочистка 24-2000 → блендинг.
Она собирает состояние установок, прогнозирует качество продукта, перебирает
возможные изменения режима и выдаёт оператору одну безопасную рекомендацию с
объяснением. Если надёжного решения нет, система говорит об этом прямо и
не выдаёт рискованный совет.

Хакатон «Нефтекод», задача по управлению режимом производства ДТ.

## Зачем это производству

Мы посчитали по выгрузке поточного анализатора за 2023-2026 годы: медиана
серы в товарном ДТ 8.4 мг/кг при лимите 10, и **12.05% времени продукт идёт
выше лимита**. По годам разброс заметный: 11.5 / 16.1 / 6.9 / 14.8 процента.

Отсюда следует главное про ценность. Она измеряется не средним снижением
серы, а сокращением доли времени вне спецификации, причём без потери отбора
дизельной фракции. Ужесточить режим «на всякий случай» умеет и оператор без
всякой системы: поднял температуру реактора, получил запас по сере, заплатил
топливом и ресурсом катализатора. Ценность в том, чтобы вмешиваться только
когда нужно, ровно настолько, насколько нужно, и не трогать установку, когда
запас и так есть.

Поэтому три вещи, которые система делает всегда:

- в устойчивом режиме она не предлагает ничего и объясняет, почему запаса
  достаточно;
- при риске нарушения спецификации выбирает минимальное достаточное
  воздействие, а не максимально безопасное;
- при плохих данных или сомнительном прогнозе отказывается от рекомендации
  и показывает, чего именно не хватает.

## Быстрый старт

Нужен Python 3.11. На macOS LightGBM дополнительно требует системную
библиотеку OpenMP, без неё не импортируется вообще ничего.

```bash
brew install libomp                  # только macOS
pip install -r requirements.txt
python run.py demo
```

Полный прогон трёх сценариев занимает около 15 секунд, из них 7 секунд
уходит на чтение исторических рядов из `data/`. Если данных организаторов
под рукой нет, система запустится и без них: подробности ниже, в разделе
про данные.

Проверка тестами, 110 штук, около двух с половиной минут:

```bash
python -m pytest tests -q
```

Три сценария из технического задания, все на одном и том же моменте времени
14 марта 2026, 08:20. Числа ниже получены последним прогоном, а не написаны

| Сценарий | Ситуация | Что делает система | Результат |
|---|---|---|---|
| `normal` | режим устойчив, сера 8.4 мг/кг | не предлагает изменений | запас 0.76 мг/кг, 99 вариантов проверено, все допустимы |
| `quality_risk` | отбор поднят, реактор холоднее, сера 9.3 | поднять температуру реактора с 366.5 до 369.0 °C | запас 0.13, отбор не режем, 45 вариантов из 99 прошли фильтр |
| `degraded_data` | лабораторный анализ 52-часовой давности, анализатор залип | отказ от рекомендации | доверие 0.00 с разбивкой по причинам |

Запустить по одному:

```bash
python run.py demo --scenario quality_risk
python run.py demo --no-telemetry        # быстро, без исторических рядов
```

Отчёт печатается по структуре раздела 5 технического задания: время и
состояние, проблема, предлагаемое действие в виде «было → стало», ожидаемый
эффект, проверка ограничений, уверенность, объяснение. К ним добавлены три
блока: допустимые альтернативы с ценой выбора, допущения и обмен между
агентами.

## Как устроена система

Пять уровней. Два из них не содержат ни моделей, ни языковых моделей, и это
архитектурное решение, а не экономия сил.

```
   L0  Сборка состояния                   чистый код
       as-of join по времени, возраст анализов, флаги качества данных
                          |
                          v
       +------------------+------------------+
       |                  |                  |
   L1a Качество      L1b Надёжность    L1c Самоконтроль
   прогноз + интервал  severity +        сверка прошлых
                       allowed_ranges    прогнозов с ЛИМС
       |                  |                  |
       +------------------+------------------+
                          v
   L2  Оптимизация: кандидаты внутри trust region
                          v
   L3  Жёсткий фильтр                      чистый код, без LLM
       сравнение чисел с config/constraints.yaml
                          v
   L4  Оркестратор: лексикографический выбор, объяснение, трейс
                          v
              Рекомендация или обоснованный отказ
```

### Кто с кем разговаривает

Мультиагентность здесь не в количестве классов, а в том, что агенты реально
ограничивают друг друга. Ниже точный обмен: что агент получает, что отдаёт и
как это меняет поведение остальных.

| Агент | Файл | Получает | Отдаёт | Как влияет на других |
|---|---|---|---|---|
| Качества | `agents/quality.py` | состояние, предлагаемое изменение режима | прогноз показателей с интервалом, риск нарушения спеки, доверие к данным | его прогноз проверяет фильтр, по нему же оркестратор сравнивает варианты |
| Надёжности | `agents/reliability.py` | состояние, история телеметрии | индекс и класс тяжести режима, факторы риска, допустимые диапазоны | **сужает границы оптимизатору**: выйти за них тот не может |
| Самоконтроля | `agents/model_monitor.py` | прошлые прогнозы, новые анализы ЛИМС | покрытие интервала, статус модели, множитель ширины | **расширяет интервал агента качества** и может заблокировать выдачу рекомендации |
| Оптимизации | `agents/optimizer.py` | состояние, допустимые диапазоны | набор вариантов изменения режима с оценкой каждого | для каждого варианта вызывает агента качества |
| Жёсткий фильтр | `gate.py` | вариант, состояние, конфиг ограничений | вердикт: прошёл или нет, запасы, предупреждения | отбраковывает варианты, ни один агент не может это обойти |
| Оркестратор | `orchestrator.py` | все оценки и вердикты | итоговая рекомендация или отказ, объяснение, трейс | разрешает конфликт целей, решает, выдавать ли совет |
| Помощник | `llm/` | готовый трейс решения | ответы на вопросы оператора словами | ничего не решает и не считает |

Один цикл выглядит так:

1. собрали состояние на момент времени, посчитали возраст каждого анализа;
2. агент самоконтроля сверил прошлый прогноз с новым лабораторным анализом
   и задал ширину интервала;
3. агент качества дал прогноз серы, агент надёжности - тяжесть режима и
   границы;
4. если по сере нет ни одного пригодного измерения или модель систематически
   промахивается, цикл останавливается отказом;
5. оптимизатор построил 99 вариантов внутри границ, каждый оценён агентом
   качества;
6. фильтр проверил каждый вариант по 13 числовым ограничениям;
7. оркестратор выбрал лучший по лексикографическому правилу;
8. отчёт напечатан, трейс сохранён, на вопросы по нему можно спрашивать.

### Разрешение конфликта целей

Порядок критериев строгий, не взвешенная сумма:

1. жёсткие ограничения, проверяет фильтр;
2. достаточен ли запас по спецификации;
3. величина воздействия, меньше значит лучше;
4. тяжесть режима;
5. экономика.

Экономика стоит последней сознательно: недопустимый режим нельзя оправдать
ни производительностью, ни затратами. Величина воздействия выше тяжести и
экономики, потому что в устойчивом режиме установку вообще не надо трогать.

## Инженерные решения, на которых всё держится

**Предлагает агент, проверяет код.** Модуль `gate.py` не импортирует ничего
из `agents/` и не обращается к языковой модели. Он только сравнивает числа с
конфигом. Ни один вариант не пройдёт за счёт убедительного объяснения. На
это есть тест, который разбирает импорты файла и падает, если зависимость
появится.

**Проверка по консервативной границе интервала.** Для серы берётся верхняя
граница прогноза, а не среднее. Прогноз 9.6 при лимите 10 выглядит
безопасно, но с интервалом плюс-минус 0.8 верхняя граница равна 10.4, то
есть риск реальный.

**Уровень даёт измерение, модель даёт эффект действия.** Абсолютный прогноз
серы честен, но его интервал шириной около 4.5 мг/кг при лимите 10 не
проходит проверку никогда, даже для варианта «ничего не менять». Поэтому
уровень берётся из измерения (анализатор каждые 10 минут, лаборатория
несколько раз в сутки), а модель отвечает только за разницу между текущим и
предлагаемым режимом. Это стандартный приём инференциального управления, а
не ослабление проверки.

Ширина интервала собрана из трёх слагаемых: эмпирический квантиль роста
серы за время, прошедшее с анализа (таблица в `config/constraints.yaml`,
посчитана по 175 тысячам точек анализатора), расхождение лаборатории и
анализатора, и доля предсказанного эффекта, которая может не реализоваться.

**Жёсткое и мягкое разделены.** Требование спецификации одно: сера не выше
10 мг/кг. Пороги по вспышке, ПТФ и плотности мы задали сами, и техническое
задание прямо запрещает выдавать собственное допущение за промышленный
предел. Поэтому по ним фильтр не отбраковывает, а предупреждает: в отчёте
это строка `[~] ВНИМАНИЕ (модельное допущение)`. Диапазоны управляемых
переменных и размер шага при этом жёсткие, потому что шаг это защита от
экстраполяции модели.

**Режим восстановления.** Если продукт уже вне спецификации, формально
отбраковываются все варианты и система должна молчать. Но молчать в этот
момент хуже всего. Оркестратор выбирает вариант, который улучшает запас и не
нарушает больше ничего, и прямо пишет, что за один шаг спецификация не
восстанавливается. Нарушение не прячется, оно печатается как `[!] НАРУШЕНО`.

**Система следит за собой.** Агент самоконтроля хранит прошлые прогнозы и
сверяет их с приходящими лабораторными анализами. На демо-моменте это 30
сверок: интервал накрыл лабораторию в 90% случаев при заявленных 90%, и
агент расширил интервал в 1.17 раза, компенсируя небольшую оптимистичность
модели. Если покрытие падает ниже 65%, система перестаёт давать
рекомендации: данные могут быть свежими, но доверять прогнозу нельзя.

**Языковая модель объясняет, но не решает.** Отчёт собирается кодом и
самодостаточен. Помощник нужен для вопросов, которых в шаблоне нет.

```bash
echo "GEMINI_API_KEY=ваш-ключ" > .env
python run.py ask --scenario quality_risk "почему не подняли температуру сильнее?"
```

Ответ на этот вопрос из реального прогона: «Температуру реактора подняли на
2.5 °C (с 366.5 до 369.0), так как это максимально допустимый шаг изменения
для данной переменной».

Безопасность здесь держится на трёх ограничениях. Модель не участвует в
принятии решения: без ключа и без сети рекомендации те же самые, меняется
только форма ответа на вопрос. Каждое число из ответа сверяется с данными
решения, и не найденное помечается как неподтверждённое. В модель уходит
только сжатый трейс, своих источников у неё нет.

## Качество моделей

Сера моделируется с нуля: готовой формулы виртуального анализатора на неё
нет ни на одном листе выданного справочника. Остальные показатели там есть,
и мы используем их как опорную линию, а машинное обучение работает только на
остатке, который формула не объясняет.

| Показатель | Как считается | Качество |
|---|---|---|
| Сера в товарном ДТ | Аррениус как опорная линия + LightGBM на остатке, монотонные ограничения по знаку | RMSE 2.28 на отложенном тесте |
| Температура вспышки | готовый виртуальный анализатор из справочника + остаток | RMSE 5.19 против 7.08 у константы, покрытие интервала 80% |
| Конец кипения сырья | формула ВАК + остаток | остаток снижает ошибку на 44% относительно чистой формулы |

Цифру по сере важно читать правильно. Мы измерили, насколько расходятся два
физических прибора, меряющих одно и то же: лабораторный анализ и поточный
анализатор в пределах 15 минут друг от друга дают RMSE 2.25 при 1400 парах
наблюдений. Модель с RMSE 2.28 находится в трёх сотых от этого предела.
Дальнейшее снижение ошибки упирается не в алгоритм, а в согласованность
самих измерений, и именно поэтому система строит решение вокруг измеренного
уровня, а не вокруг прогноза.

Валидация строго по времени, перемешивание строк запрещено. Отдельно
проверено, что калибровочная выборка не использовалась для отчётных цифр:
на переиспользованной калибровке RMSE получался 1.67, на честном отложенном
тесте 2.28, и в отчёт идёт вторая цифра.

Без этих файлов демо всё равно запустится: система скажет, что исторических
рядов нет, агент надёжности посчитает два фактора из пяти вместо всех,
а агент самоконтроля останется непрогретым. Обученные модели лежат в
`artifacts/models/` и в данных не нуждаются.

### Что мы нашли в данных, и что из этого следует для кода

**Сера работает вплотную к лимиту.** 189 649 точек анализатора с шагом 10
минут, медиана 8.4 при лимите 10, 12.05% времени выше лимита. Поэтому
система оптимизирует долю времени вне спеки, а не среднее.

**Анализаторы залипают, и это видно.** Пропусков во времени нет, но есть 67
эпизодов замороженного значения дольше часа, самый длинный 1122 часа, это 47
суток. Детектор залипаний работает в `loaders.detect_stuck()`, залипшее
значение сохраняется, но помечается как неисправное.

**Значения-маркеры.** У восьми колонок гидроочистки максимум ровно 307.00, у
трёх ровно 10.00, расходы уходят в минус до -23.75. Это не измерения, и они
вычищаются отдельным правилом.

**Справочник КИП местами не совпадает с данными.** Тег `242000:T18`
подписан как давление на выходе колонны, но принимает значения 50-100 с
медианой 68.7 и коррелирует на 0.62 с лабораторной температурой вспышки.
Мы используем его как виртуальный анализатор вспышки, а все спорные коды
помечены `verified: false` в `config/tags.yaml`.

**Серу линейно из телеметрии не видно.** Максимальная корреляция любой из 26
колонок гидроочистки с серой анализатора 0.23 по модулю. Для сравнения:
вспышка ловится с 0.62, плотность с 0.53. Отсюда лаги, волатильность
температуры реактора и нелинейные модели.

**Часть формул справочника содержит члены вида `LIMS:...`.** Использовать
такую формулу как прогноз и проверять её по тому же лабораторному анализу
значит смотреть в будущее, поэтому такие члены заменяются последним
доступным значением с известным возрастом.

## Воспроизводимость

Каждый прогон пишет трейс в `artifacts/traces/`. Имя содержит и момент
решения, и момент записи, поэтому повторный прогон не затирает предыдущий.
Внутри полный след цикла: состояние, оценки всех агентов, каждый
рассмотренный вариант с его вердиктом и запасами, итоговая рекомендация.

Отдельный блок `meta` отвечает на вопрос, чем именно получен результат:
коммит, версия Python, идентификаторы моделей, версии библиотек и
контрольные суммы всех конфигов. Пороги и диапазоны лежат в YAML, то есть их
правка меняет решение так же, как правка кода, и хэш это фиксирует.

Отчёт восстанавливается из файла без единого пересчёта:

```bash
python run.py replay
```

Трейс компактный, около 85 КБ на цикл: список выполненных проверок хранится
один раз, а не копией у каждого варианта, числа округляются до четырёх
знаков. Сами варианты и их запасы сохраняются целиком, иначе трейс перестал
бы доказывать, почему решение именно такое. Полный дамп с отступами
снимается вызовом `save_trace(..., full=True)`.

Сценарии демо независимы друг от друга: агент самоконтроля копит память
между циклами, поэтому перед каждым сценарием ему выдаётся одна и та же
прогретая копия. Без этого результат зависел бы от порядка запуска, причём
незаметно. На это есть отдельный тест.

## Допущения

Все допущения помечены в конфигах полем `source: assumption` и печатаются
оператору в блоке «Допущения».

- Требование спецификации одно: сера не выше 10 мг/кг. Пороги по вспышке,
  ПТФ и плотности наши, поэтому они предупреждают, а не отбраковывают.
- Диапазоны управляемых переменных заданы консервативно по истории, между
  5-м и 95-м перцентилем. Исторический минимум и максимум не выдаются за
  промышленный предел.
- Максимальный шаг за цикл равен 90-му перцентилю фактического часового
  изменения параметра: система не предлагает движений крупнее тех, что
  оператор делает сам.
- Дата начала цикла катализатора неизвестна, принята 1 января 2023 года.
- WABT считается по стандартной отраслевой формуле для адиабатического
  реактора, вход реактора надёжно не опознан среди тегов, поэтому пока
  используется температура выхода как прокси.
- Состав дизельного пула для блендинга принят как два потока с АВТ, доли
  проверяются по историческому окну пропорции.
- Стоимостной прокси выражен в условных единицах: фактических экономических
  данных в пакете нет.

## Ограничения и что дальше

Мы предпочитаем назвать слабые места сами.

- Отклик конца кипения на отбор дизельной фракции у модели АВТ немонотонен:
  движение в обе стороны снижает прогноз. Из-за этого при шуме датчиков
  порядка 0.3% совет по расходу может менять знак. Лечится монотонными
  ограничениями по входам формулы, это следующая задача.
- Переменная `AVT:F32` числится управляемой, но в признаки модели конца
  кипения не входит, поэтому её изменение не влияет на прогноз. Нужно либо
  ввести её в модель, либо убрать из активных.
- Ключ Парето-фронта не учитывает выпуск, а затраты и тяжесть режима оба
  зависят только от температуры реактора, поэтому фронт вырождается. Пока в
  альтернативах показываются крайние точки компромисса по каждому критерию.
- Система советует, а не управляет. Замыкание контура потребовало бы
  промышленных блокировок и сертификации, а не фильтра на Python.
- Обратная связь по новым анализам подключена только к ширине интервала.
  Дообучение моделей по мере поступления лабораторных данных не сделано.
